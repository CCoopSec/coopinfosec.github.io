## Overview
I have been researching the security posture of the CloudEdge Bell 24T doorbell for a few months shy of a year, taking it on as my first IoT vulnerability research project. This has been an incredibly rewarding experience for not only the findings, but also the vast amount of knowledge gained along the way. Several vulnerabilities have been discovered and are pending CVE ID's, the first one of the bunch being the complete lack of TLS certificate validation by the firmware.

In a secure IoT architecture, the device should not blindly trust any certificate presented to it. Best practice for such devices would be to use Certificate Pinning (firmware is hardcoded to only trust the specific cryptographic hash or public key of the vendor's official server certificate). Even without pinning, the device should at least verify that the certificate was signed by a recognized Certificate Authority (CA). Because I did not have root access to the doorbell to manually install a custom root CA into its trust store, I had to present the the doorbell with my own self signed certificate and see if it would accept it without dropping the connection.

I have identified **CWE-295: Improper Certificate Validation** (a complete lack of **Certificate Pinning**).

Because I did not have root access to the doorbell to manually install the `mitmproxy` root CA into its trust store, the doorbell accepted an untrusted, self-signed certificate without dropping the connection.

This was done so by deploying a transparent proxy and executing a**Man-in-the-Middle (MitM) Attack** by weaponizing the routing capabilities of my raspberry pi gateway setup to work with `mitmproxy`: 

1. Configure the Interception Environment:
Used hostapd to convert the wlan0 network interface into an access point, allowing the Raspberry Pi to broadcast a dedicated SSID and act as the doorbell's local router. Paired with dnsmasq, the Pi functioned as a DHCP/DNS server to automatically assign IP addresses and route the video doorbell's outbound traffic.
Because the doorbell is connected to the access point hosted on the `wlan0` interface, all of its outbound traffic must pass through the gateway. By tweaking `iptables` rules on the gatweay, a forced reroute of selected traffic is possible.

3. Set Up the Proxy & Port Forwarding:
Launched mitmproxy as a transparent proxy and configured it to listen on port 8081:
`mitmproxy --mode transparent --showhost -p 8081 -k`
Now that Mitmproxy is listening on port 8081 in transparent mode (the client is unaware of its existence), when the doorbell attempts to establish a secure TLS connection with its cloud server, mitmproxy intercepts this request and dynamically generates a forged SSL/TLS certificate for whatever domain
the doorbell is trying to reach. Mitmproxy then establishes its own secure connection to the actual cloud server. The doorbell has no idea its traffic is being diverted; it thinks it's talking directly to the cloud server. Mitmproxy decrypts the traffic from the doorbell using the forged certificate, logs the plaintext data to your screen, re-encrypts it using the legitimate cloud server's certificate, and sends it on its way.


To get all of these packets to be sent to mitmproxy instead of the upstream interface, I configured iptables on the Raspberry Pi to redirect all incoming traffic destined for port 443 to the proxy's listening port (8081). Iptables rule used:
		- `sudo iptables -t nat -A PREROUTING -i wlan0 -p tcp --dport 443 -j REDIRECT --to-port 8081`
It looks at any traffic entering `wlan0` that is trying to reach port 443 (HTTPS) and silently redirects it to local port 8081.

The CloudEdge Bell 24T fails to properly validate SSL/TLS certificates when communicating with its backend cloud infrastructure. The absence of certificate pinning and chain validation in the firmware allows an attacker to intercept, decrypt, and manipulate 'secure' HTTPS communications to port 443 via a Man-in-the-Middle (MitM) attack.


By routing the device's traffic through a rogue wireless access point paired with a transparent proxy, an attacker can completely compromise the confidentiality and integrity of the device-to-cloud communication stream. 
- **Information Disclosure:** Silent interception of video feeds, account identifiers, session tokens, and potentially plaintext credentials.
- **Data Modification:** Tampering with API requests and responses (e.g., spoof status events, inject custom payloads, utilize paid features without payment, or modify device configuration states).

**Impact:** In the real world, if a user connected this doorbell to a compromised network or a malicious public Wi-Fi hotspot, an attacker could silently intercept, read, and modify all data flowing between the doorbell and the cloud, including potentially viewing the video feed, stealing authentication tokens, or capturing plaintext credentials.

  

## Recommended Mitigation:
---
- **Certificate Validation:** The firmware must be updated to enforce strict validation of the SSL/TLS certificate chain against a trusted root CA store.
- **Certificate Pinning:** Implement public key or certificate pinning for all communications between the physical device and the Meari Technologies backend APIs to explicitly reject arbitrary or self-signed certificates.
