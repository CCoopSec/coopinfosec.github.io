## Overview
I have been researching the security posture of the CloudEdge Bell 24T doorbell for a few months shy of a year, taking it on as my first IoT vulnerability research project. This has been an incredibly rewarding experience for not only the findings, but also the vast amount of knowledge gained along the way. Several vulnerabilities have been discovered and are pending CVE ID's, the first one of the bunch being the complete lack of TLS certificate validation by the firmware.

Since IoT devices commonly have one primary communication channel, the device should not blindly trust any certificate presented to it when it comes to establishing said secure cummincation channels. The practice for such devices would be to use Certificate Pinning, which ensures the firmware is hardcoded to only trust the specific public key or hash of the vendor's official server certificate. Even without pinning, the device should at least verify that the certificate was signed by a recognized Certificate Authority (CA). Because I did not have root access (yet) to the doorbell to manually install a custom root CA into its trust store, I had to present the the doorbell with my own self signed certificate and see if it would accept it without dropping the connection.

This was done so by deploying a transparent proxy and executing a **Man-in-the-Middle (MitM) Attack**. By weaponizing the routing capabilities of my Raspberry Pi to work with `mitmproxy`, I was able to capture, analyze, manipulate, and repeat network traffic leaving and entering the doorbell. ## Interception Environment
I used `hostapd` paired with `dnsmasq` and some `iptables` rules to convert the Wi-Fi card of the Pi (wlan0 interface) into a wireless access point, allowing for full traffic interception, masquerading, and redirection.
I then used `mitmproxy` to act as a transparent proxy (the client is unaware of its existence) listening on port 8081:
`mitmproxy --mode transparent --showhost -p 8081 -k`

When the doorbell attempts to establish a secure TLS connection with its cloud server, mitmproxy intercepts this request and dynamically generates a forged SSL/TLS certificate for whatever domain the doorbell is trying to reach and presents it back to the doorbell. Mitmproxy then establishes its own secure connection to the actual cloud server. The doorbell has no idea its traffic is being diverted; it thinks it's talking directly to the cloud server. `mitmproxy` then decrypts the traffic from the doorbell using the forged certificate, logs the plaintext data to your screen, re-encrypts it using the legitimate cloud server's certificate, and sends it on its way.

To get all of these packets to be sent to `mitmproxy` instead of the upstream interface, I set more iptables rules on to redirect all incoming traffic destined for port 443 to the proxy's listening port (8081): 
`sudo iptables -t nat -A PREROUTING -i wlan0 -p tcp --dport 443 -j REDIRECT --to-port 8081`

After getting this MiTM environment setup, I then connected the Doorbell to the access point's SSID manually using the paired app on my phone and triggered actions that involved TLS communication from both the doorbell and the mobile app. The doorbell does not drop the connection upon receiving the proxy's untrusted, self-signed certificate during the handshake for establishing the TLS tunnel. The handshake completes successfully without triggering any certificate pinning or chain validation failure routines. Decrypted HTTPS/TLS traffic to and from the doorbell is fully visible and editable in the proxy.

### Recommended Mitigation:
- **Certificate Validation:** The firmware must be updated to enforce strict validation of the SSL/TLS certificate chain against a trusted root CA store.
- **Certificate Pinning:** Implement public key or certificate pinning for all communications between the physical device and the Meari Technologies backend APIs to explicitly reject arbitrary or self-signed certificates.
